# 技术方案

产出能指导开发和评审的技术方案。先说明采用什么方案，再展开实现；让读者看懂改哪里、数据怎么走、关键逻辑是什么、如何验收。

## 工作方式

1. 结合用户需求、已有方案和可访问代码，确认目标、当前实现与本期功能。已有代码时先查入口、关键调用和受影响模块，再提出改法；资料不足时明确方案假设，不虚构现状。
2. 按 [报告格式](references/report-format.md) 组织内容。这是内置的通用模板，无须访问外部文档；用户提供其他模板时再读取并采用对应格式。新文档沿用主线并按规模裁剪，修改已有文档时保留有效内容、原优先级和来源。
3. 先确定模块职责、关键接口和数据流，再写图与功能设计。存在实质取舍时，用短表说明推荐方案、原因及代价；没有取舍就直接写采用的方案。
4. 每项本期核心功能都给出实现机制和核心伪代码；用架构图解释模块关系，用时序图解释关键执行过程。功能、图、代码中的对象和接口使用同一套名称。
5. 补齐与本次改动直接相关的监控、影响、验收和任务拆分，最后做一次去重与一致性检查。

默认直接完成文档；只有缺失信息会改变方案方向时才提问，并继续处理不依赖答案的部分。负责人、日期、性能数字、版本和评审结论没有依据时不编造；假设或待确认事项集中放一处。

## 简练表达

- 默认中文，保留必要的代码标识符。每段先给结论，通常 2–4 句；比较、映射、需求和排期使用短表，不把长段落硬塞入表格。
- 背景只交代问题与目标，需求只列本期范围；技术方案篇幅主要用于实现。删除不影响实现或评审的铺垫、口号和重复总结。
- 不单设通用的“设计基本原则”或“安全边界”章节。兼容、权限、数据和生命周期等确实影响实现时，只在最相关的位置写具体规则、分支或取舍；其他章节引用该处，不重复论证。
- 避免“确保安全可控、保持低耦合、遵循最佳实践”等空话，改成具体动作，例如“按 requestId 丢弃旧请求回包”。用户要求简短不等于省略影响行为的失败分支。
- 同一事实、决策、风险或待办只完整描述一次。需求表写结果，设计写机制，验收写可观察行为；不要在多个章节复述同一说明。
- 拟议接口与已存在接口首次出现时区分清楚。资料来源和验证状态集中用一句说明；没有实施证据时使用“拟新增”“预期”等准确表述，不在各章反复追加“未读代码、尚未实现、尚未验证”的提醒。

## 图示要求

完整方案至少包含一张整体架构图和一张关键时序图。仅修改局部章节时，复用并同步更新已有相关图，不为满足数量复制无关图。

- **架构图**：默认 Mermaid `flowchart`。标出业务入口、核心模块、外部依赖以及实际涉及的数据存储；连线写调用或数据含义。重构时区分现有与新增模块。图按职责分组，过大时拆出局部图，避免把所有类塞入一张图。
- **时序图**：默认 Mermaid `sequenceDiagram`。覆盖用户触发、关键调用、状态变化和最终结果；用 `alt` / `opt` / `par` 表达影响方案的失败、取消、异步或并行路径。执行顺序有独立决策的核心流程单独成图；同构流程可共享一图并注明适用功能。
- 图放在解释它的章节附近，配 1–2 句阅读提示即可。不要用“后续补图”代替图，也不要用装饰性的“客户端 → 服务端”两节点图代替模块设计。
- Markdown 交付使用完整、闭合的 Mermaid 代码块。用户要求写入飞书且环境提供 lark-doc / lark-whiteboard 技能时，按对应技能将图落为可阅读图形并读回检查；相关工具不可用或目标不支持图渲染时，交付 Markdown 和图源并说明限制，不声称已写入或渲染。

## 核心功能写法

每项本期核心功能依次写：

1. **行为与入口**：一句话说明触发条件、输入和预期结果。
2. **实现**：指出改动模块、关键接口、必要的数据或状态，以及本功能独有的分支。少量字段可就地列出，共享契约只定义一次。
3. **图示**：引用覆盖它的时序图；只有新增结构或独立流程需要补图。
4. **核心伪代码**：表达核心决策和状态变化，通常 10–30 行，复杂时按职责拆分。优先贴近项目主语言；技术栈未知时使用清楚的中性伪代码。
5. **验收**：给出能观察到结果的场景，或引用统一验收矩阵中的对应行。

伪代码包含输入、输出、关键分支和核心调用；涉及状态、并发、取消或资源释放时明确其变化。可调用职责已经说明的外部接口，但不能把待设计的核心逻辑藏进 `handleBusiness()`、`process()`、`doSomething()` 或省略号。不能仅给接口声明、getter/setter 或业务接入示例来代替实现伪代码，也不需要展开日志、样板代码和无关工具实现。仅列为后续阶段的功能保留概要即可。

## 交付前检查

将以下检查用于修改草稿，不默认再输出一份长检查清单：

- 本期需求是否都对应具体实现、伪代码和可观察的验收结果？
- 架构模块、时序参与者、消息与代码调用是否对应，分支和状态转换是否一致？
- 图是否完整可读，代码是否展示真正需要设计的逻辑？
- 事实是否有来源，拟议设计、假设和已验证结果是否区分准确？
- 是否还有重复原则、边界、风险、无内容章节或虚构排期、评审结论？

默认交付 Markdown。用户指定飞书或其他文档载体时遵从其要求；引用参考文档本身不代表要修改那篇文档。只要求技术方案时不顺带修改业务代码。
